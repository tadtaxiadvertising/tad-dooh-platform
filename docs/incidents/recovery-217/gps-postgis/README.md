# #217 — exact GPS/PostGIS storage contract

**IMPLEMENTADO, PENDIENTE DE VERIFICACIÓN.** The source changes qualify GPS SQL against `public.telemetry` and PostGIS functions/types in `extensions`. The read-only startup catalog verifies the native geography namespace, Point shape, SRID 4326, two dimensions and NOT NULL. Missing or incompatible storage still prevents API startup. No schema write runs at startup.

`TelemetryService.sync` rejects a complete batch with HTTP 400 and `TELEMETRY_COORDINATES_INVALID` before opening a transaction when any point has missing, nonnumeric, nonfinite or out-of-range latitude/longitude. PostGIS geography conversion can normalize coordinates, so the service must reject invalid input before conversion. Valid boundaries and zero coordinates remain accepted. Existing parameterization, longitude/latitude order, chunking, one-transaction rollback, per-second deduplication and acknowledgement behavior are preserved. Timestamp and speed policy remain outside this change.

`J-gps.sql` is a clone-only draft outside migrations, workflows and runtime startup. It requires the owned `restored` database, Unix-socket bootstrap access, explicit recovery marker, expected table ownership/types, existing dedup index and empty telemetry under lock. It requires the existing `extensions` schema and available pinned PostGIS 3.3.7, installs the extension through the local bootstrap, and adds `extensions.geography(Point,4326) NOT NULL`. It neither invents historical taxi locations nor changes managed spatial reference ownership/RLS. Repeated execution and incompatible preconditions abort atomically. The version is an isolated rehearsal pin, not an instruction to install that version on the hosted provider.

Verification uses actual PostgreSQL geography constraints and the actual compiled service with real native Prisma transactions. Only Nest decorators/logging are stubbed in the auxiliary probe. The synthetic probe commits valid fixture rows and proves a later-chunk failure rolls back earlier writes. The restored-data probe wraps future fixture rows in a transaction and uses savepoints to keep the entire probe reversible; it does not certify a committed production write. Counts and booleans are emitted without coordinates, identifiers or original row values. The restored database has default function privileges, so installing PostGIS adds explicit ACL entries for its new functions. Each allowed new routine must be a bootstrap-owned PostGIS extension member with ACL exactly matching the pre-existing global/schema creation defaults. Its definition, configuration and aggregate bindings must match an independent pristine installation of the pinned extension. Stock PostGIS 3.3.7 includes three SECURITY DEFINER overloads of ST_EstimatedExtent; only those exact oracle-matched definitions are allowed. They are managed extension objects and are not rewritten. Production function exposure and tenant access remain separate release gates. Catalog identities are rendered with only pg_catalog on the metadata session search path, and aggregate ACL identities omit argument names to match pg_dump. A restored-style search path is reproduced in the synthetic fixture. Existing extension functions retain exact definitions and permissions; only those audited new ACL entries are excluded from the old-object dump comparison. Exact original projections, roles, unallowlisted catalog and schema dumps are checked, and owned containers/network and the temporary encrypted key are removed. Executed results and limits belong in `verification.json`.

The rehearsal rollback is disposal of the owned clone. Production transition still requires independent recovery-key custody, essential configuration, #244/#313 controls, full API/Auth/player/RBAC/FK verification, load coverage and an operational rollback plan. A successful local proof does not establish the deployed revision or production health. No production DDL is included in this source publication.
